# CRONOS v0.2.0 - Fase 4: Retrieval Engine

Data: 2026-07-21
Branch: `feature/v0.2.0-memory-knowledge`

## Objetivo

Criar a primeira camada desacoplada de inteligencia semantica do CRONOS para atender Biblioteca, Memoria, livros, procedimentos, programacao, conversas e aprendizado em fases futuras.

Esta fase nao implementa interface grafica, voz, automacoes, controle do computador, multiplos modelos em UI ou Qdrant.

## Arquitetura

Componentes adicionados:

- `backend/cronos/core/retrieval_config.py`
- `backend/cronos/repositories/retrieval_repository.py`
- `backend/cronos/services/embedding_provider.py`
- `backend/cronos/services/embedding_service.py`
- `backend/cronos/services/lexical_search_service.py`
- `backend/cronos/services/reranking_service.py`
- `backend/cronos/services/retrieval_service.py`

A logica permanece fora de `server.py`. O servidor apenas despacha as rotas para `library_routes.py`.

## Provider de Embeddings

Interface abstrata:

- `initialize()`
- `is_available()`
- `embed_documents()`
- `embed_query()`
- `dimension()`
- `model_name()`
- `health()`

Nome arquitetural da interface publica:

- `SemanticProvider`

No codigo atual, essa interface esta implementada como `EmbeddingProvider`.

Provider concreto padrao da v0.2.0:

- provider: `cronos-local-semantic`
- operacao: local e offline
- downloads automaticos: nao
- dependencia obrigatoria de Hugging Face: nao
- dependencia obrigatoria de `sentence_transformers`: nao
- dimensao esperada: `384`

O provider proprio do CRONOS e a implementacao oficial da v0.2.0. Se ele nao carregar ou falhar durante execucao, o CRONOS continua funcionando em modo lexical, sem travar inicializacao, login, chat ou biblioteca.

Providers adicionais poderao ser adicionados futuramente sem alterar a API publica:

- Sentence Transformers;
- ONNX;
- GGUF;
- TensorRT;
- CUDA;
- outros providers locais.

Provider de teste:

- `DeterministicEmbeddingProvider`
- usado apenas nos testes para validar fluxo sem download de modelo.

## Embeddings

Migration adicionada:

`0004_retrieval_embeddings_schema`

Tabela `document_embeddings` consolidada com:

- `document_id`
- `chunk_id`
- `provider`
- `model`
- `dimension`
- `embedding`
- `embedding_hash`
- `created_at`
- `updated_at`

O repositório usa upsert por `chunk_id`, `provider` e `model`, evitando embeddings duplicados. Se o modelo mudar, novos embeddings podem coexistir sem quebrar os anteriores.

## Indexacao

Fluxo:

documento -> paginas -> chunks -> embedding -> armazenamento -> indexacao concluida

A indexacao e incremental:

- chunks ja indexados para o provider/modelo atual sao pulados;
- `force = true` recalcula embeddings;
- troca de provider/modelo cria novo conjunto;
- documentos sem embeddings continuam pesquisaveis lexicalmente.

## Retrieval

Fluxo de consulta:

consulta -> busca lexical -> busca semantica quando disponivel -> normalizacao -> combinacao -> reranking -> resultado

Mesmo sem embeddings, o resultado lexical permanece funcional.

Cada item retorna:

- `document`
- `page`
- `chunk`
- `citation`
- `score_lexical`
- `score_semantic`
- `score_final`
- `excerpt`

## Reranking

O reranking combina:

- score lexical;
- score semantico;
- proximidade textual;
- recencia;
- prioridade futura.

Os pesos ficam centralizados em `retrieval_config.py`, sem constantes espalhadas.

## APIs

Novas APIs:

- `POST /library/retrieve`
- `GET /library/index/status`
- `GET /library/index/providers`
- `POST /library/index/rebuild`

Entrada de `/library/retrieve`:

```json
{
  "query": "texto da consulta",
  "top_k": 8,
  "filters": {
    "document_id": 1,
    "source_id": 1,
    "page_number": 1
  }
}
```

## Compatibilidade

Documentos antigos continuam pesquisaveis. O retrieval usa os chunks existentes da Fase 3 e chama a indexacao legada quando necessario. Embeddings sao uma melhoria incremental: a busca hibrida usa o provider local quando disponivel, e a busca lexical permanece funcional como fallback.

## Seguranca

- Conteudo de documentos nunca e executado.
- Documento nao e tratado como instrucao de sistema.
- Embeddings completos nao sao registrados em auditoria ou logs.
- Erros do provider sao sanitizados no `health`.
- O fallback lexical evita falhas de disponibilidade do modelo.

## Benchmark Local

Amostra com o provider oficial `cronos-local-semantic` em ambiente temporario, sem tocar no banco pessoal:

- chunks: 200
- embeddings gerados: 200
- tempo medio de geracao de embedding: 1,31 ms
- tempo de indexacao: 438,26 ms
- tempo medio de consulta: 71,57 ms
- uso aproximado de memoria: 2,38 MB de pico medido por `tracemalloc`
- embeddings processados por segundo: 456,35
- modo final: `hybrid`

Esses numeros medem o provider local oficial da v0.2.0 no pipeline real de indexacao e consulta do CRONOS. Nao dependem de internet, Hugging Face ou ambiente Python de desenvolvimento.

## Impacto no PyInstaller e Instalador

Nenhuma dependencia obrigatoria externa foi adicionada. O backend empacotado funciona com o provider local oficial e tambem continua funcionando em fallback lexical caso o provider falhe. O tamanho do executavel backend ficou em aproximadamente 14,65 MB, mantendo o mesmo perfil de empacotamento do sidecar.

## Riscos e Pendencias

- Providers adicionais como Sentence Transformers, ONNX, GGUF, TensorRT e CUDA ainda nao fazem parte da implementacao oficial.
- Sem o artefato local do provider oficial, a busca semantica fica indisponivel e o CRONOS usa apenas lexical.
- Embeddings ficam em SQLite como JSON; Qdrant permanece fora desta fase.
- A interface ainda nao consome os novos endpoints de retrieval.
- Pesos de reranking sao iniciais e devem ser calibrados com uso real.
