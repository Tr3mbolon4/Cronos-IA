# CRONOS v0.2.0 - Fase 2: memoria permanente backend

Data: 2026-07-21
Branch: `feature/v0.2.0-memory-knowledge`

## Objetivo

Implementar a base backend da memoria permanente do CRONOS sem iniciar ainda interface, biblioteca avançada, chunks, citacoes, embeddings ou busca vetorial. Esta fase deixa o dominio de memoria persistido em SQLite, auditavel, revisavel e exposto por API local autenticada.

## Componentes adicionados

- `backend/cronos/models/memory.py`: constantes e normalizacao de texto.
- `backend/cronos/schemas/memory_schemas.py`: validacoes e erros estruturados.
- `backend/cronos/repositories/memory_repository.py`: acesso transacional a memorias, categorias, revisoes e auditoria.
- `backend/cronos/repositories/memory_relation_repository.py`: acesso transacional a relacoes.
- `backend/cronos/services/memory_service.py`: regras de criacao, edicao, revisao, arquivamento, restauracao e exclusao logica.
- `backend/cronos/services/memory_relation_service.py`: regras de relacoes, duplicidade, escopo por proprietario e exclusao logica.
- `backend/cronos/api/memory_routes.py`: contratos HTTP da Fase 2.
- `backend/tests/test_memory.py`: cobertura dos fluxos de memoria, relacoes, validacoes, auditoria e rollback.

## Modelo de memoria

Status internos persistidos:

- `active`
- `archived`
- `pending_review`
- `deleted`

A interface devera traduzir esses valores para portugues em uma fase posterior. A exclusao padrao e logica: o registro recebe `status = deleted` e `deleted_at`, permanecendo restauravel. Nenhuma API de exclusao fisica foi exposta.

Campos principais:

- `owner_id`
- `category_id`
- `title`
- `content`
- `normalized_content`
- `source_type`
- `source_reference`
- `confidence`
- `importance`
- `status`
- `created_at`
- `updated_at`
- `deleted_at`

## Revisoes

Toda alteracao de memoria cria uma revisao na mesma transacao da atualizacao. A revisao registra:

- `memory_id`
- `revision_number`
- valores anteriores de titulo, conteudo, categoria, confianca, importancia e status
- `changed_fields`
- `change_reason`
- `created_at`

Se uma falha ocorre depois da revisao e antes do commit, a transacao e revertida e nem a memoria nem a revisao parcial permanecem gravadas.

## Relacoes

Tipos aceitos:

- `related_to`
- `depends_on`
- `derived_from`
- `supersedes`
- `contradicts`
- `part_of`

Validacoes aplicadas:

- a origem e o destino devem pertencer ao mesmo proprietario;
- uma memoria nao pode se relacionar com ela mesma;
- nao pode existir relacao ativa duplicada com mesma origem, destino e tipo;
- `strength` deve ficar entre 0 e 1;
- exclusao de relacao tambem e logica, por `deleted_at`;
- criacao, edicao e exclusao de relacao sao auditadas.

## Limites desta fase

Esta fase nao implementa:

- tela de Memoria;
- tela de Biblioteca;
- upload ou reprocessamento avancado de documentos;
- separacao real de PDFs em paginas e chunks;
- citacoes;
- embeddings;
- busca hibrida lexical + semantica;
- Qdrant ou banco vetorial.

Esses itens devem aguardar aprovacao explicita para a Fase 3 ou fase posterior.
